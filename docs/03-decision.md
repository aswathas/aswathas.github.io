# 03 — Decision

**Date.** 2026-10-15

## Commit a single static OG card, rendered with headless Chrome

**Decision.** `public/og.png` is a committed 1200×630 PNG. It was rendered once,
locally, by pointing headless Chrome at an HTML file and screenshotting it. Every
route references it via a new `image` prop on `Desktop.astro`, defaulting to
`/og.png`.

### What ruled out the alternatives

**A build-time `satori` endpoint** would add a rendering dependency tree to a
project whose only runtime dependency is `astro`. The build would go from
`npm ci && astro build` to `npm ci && astro build` plus a rasteriser that has to
work on whatever machine builds next. That is a real ongoing cost for a benefit —
per-page titles in preview cards — that applies to a small fraction of shares of
a portfolio site where nearly all traffic is to the root URL.

**Per-page cards via the runtime** has the same dependency problem, and one more:
a route handler that renders on every request, or a build step that renders 18
images, for the same marginal gain.

**The deciding factor** was that nothing about this site is dynamic. The name,
the role, the domain, and the tagline are constants in `src/data/site.ts`. A
static card cannot go stale relative to the content, because it is regenerated by
hand when the content changes. That is a feature for a site this size.

### What would change this decision

- If the site gained a blog with enough posts that per-post share cards became
  measurably worth it, the cost calculation flips and a build-time endpoint wins.
- If the project list on the homepage started changing weekly, a card with
  hardcoded text would drift from the page it advertises.
- If the site moved off Cloudflare Pages to a platform where committed binary
  assets are awkward, the tradeoff changes shape.

## Judge each image individually rather than applying `loading="lazy"` globally

**Decision.** The hero portrait gets `fetchpriority="high"` and `decoding="async"`.
The duplicate portrait in the right rail gets `loading="lazy"`. Icons and the
project hero icon stay eager.

### What ruled out the alternatives

**`loading="lazy"` on everything** was the reflex and it would have made the page
slower. Seven of nine images are 16–34px icons, many above the fold; lazy-loading
them adds a delay for no bandwidth or decode saving. Worse, the 963×1280 portrait
at the top of the page is very likely the LCP element — lazy-loading the largest
contentful paint candidate is precisely backwards.

**Leaving all images alone** was also considered. It is defensible on a page with
eight images, three of them gallery shots that already have the attribute. But the
page loads the same 963×1280 photograph twice, once above the fold and once in a
rail, and the one above the fold deserved to be told it matters.

### What would change this decision

If real-user monitoring ever showed a different element as LCP — the `h1` or a
text block, if fonts are already system fonts — the `fetchpriority` would move or
become unnecessary.

## Set `site` in `astro.config.mjs` once instead of hardcoding origins

**Decision.** `astro.config.mjs` declares `site: 'https://aswathas-site.pages.dev'`.
`llms.txt.ts` had its hardcoded `https://example.com` corrected to the real origin
in the same pass.

### What ruled out the alternatives

**Hardcoding the origin at each of the four use sites** is exactly what produced
the bug. `llms.txt.ts` did it, `Desktop.astro` did it in a fallback expression, and
the fallback in that expression is a plausible-looking domain that a reader has no
reason to distrust. Spreading a value across four call sites means four chances to
carry the wrong one, and in this repo three of the four were already wrong.

**Leaving the `?? 'https://example.com/'` fallbacks in place** is tempting because
they keep the types happy. They are now unreachable because `site` is set, but they
remain the exact pattern that produced `example.com` in the structured data. They
were left in place only because removing them was not worth a separate commit; they
are worth removing before someone copies them into a new endpoint.

## Render the X row, leave it dead, and stop it claiming the Instagram handle

**Decision.** The X row renders unconditionally. Its `href` falls back to `#`, it
carries `aria-disabled` while the URL is empty, and its label is `—` rather than
`@aswath_ig`. The LinkedIn row renders with the URL the user supplied.

### What ruled out the alternatives

**Hiding the row while empty**, which is what `{identity.x && ...}` did, was
tidy but it contradicted the user's instruction: "leave it just clickable go
nowhere". They want the row present. A portfolio contact page that silently omits
a channel reads as an oversight rather than a choice.

**Keeping `@aswath_ig` as the label** was never seriously viable once the row was
made visible. It would have told a visitor that `@aswath_ig` is the X account. It
is the Instagram account.

**Filling in a guessed handle** was ruled out by the source's own comment, which
said "do not guess these". The user gave LinkedIn and Instagram explicitly and
declined to give X.
